HealthLens - Concurrency Rework Comparison (v6 -> v7)
=========================================================
This compares the ORIGINAL concurrency implementation (built earlier in this
project, referred to below as "v6 / Activity Monitor") against the REWORKED
version in HealthLens-v7-concurrency-rework.zip ("v7 / Activity Centre").

This file is meant to sit alongside docs/CONCURRENCY_MAP.md, not replace it.
CONCURRENCY_MAP.md documents where each concept lives in v7 on its own terms.
This file specifically answers: "what changed, and why is v7 better?"

PART 3: WHAT'S GENUINELY NEW IN v7 (not present in v6 at all)
=========================================================

1. CountDownLatch as a start/finish gate (IntegrityCheck) - makes the race
   condition demo reliably reproducible instead of "hit or miss."
2. Future.get(timeout, TimeUnit) + cancel(true) - a hung/slow source cannot
   freeze the whole sync forever; this is closer to how a real app has to
   handle an unreliable third-party API.
3. ConcurrentHashMap and CopyOnWriteArrayList - real concurrent collections
   from java.util.concurrent, used for state that's genuinely written from
   multiple threads and read from the FX thread.
4. AtomicInteger - for simple counters that need thread-safety without a
   full synchronized block (unread count, sources reported, worker numbering).
5. A private-final-lock synchronized BLOCK (MergedReading), as opposed to
   v6's synchronized METHODS only - demonstrates the more general form of
   the pattern and explicitly documents "the monitor rule" (one lock object,
   nothing outside can synchronize on something else by mistake).
6. Safe publication of immutable state across threads (HealthSnapshot) -
   this is a genuinely more advanced correctness concept than anything in v6.
7. A single lifecycle owner (BackgroundServices) that starts and stops
   EVERYTHING in one place, in a deliberate, documented shutdown order.
8. A bounded, general-capacity queue (NotificationQueue<T>, capacity 5) with
   both a blocking put() and a non-blocking offer() - v6's Box<T> only ever
   held one slot and had no non-blocking option.
9. A listener/observer pattern (NotificationCenterService.Listener,
   SyncService.Listener) so multiple parts of the UI can react to background
   events, instead of one hard-coded callback.
10. Data-driven reminders - the reminder thread reads a real HealthSnapshot
    and only nudges the user about goals they're ACTUALLY behind on, instead
    of cycling through a fixed list regardless of their real data.
11. A visible self-diagnostic ("Diagnostics" tab) that proves, on the user's
    own machine, that the app's shared counters are correctly guarded - a
    real-world pattern (health checks / self-tests) shipped in real software.


PART 4: WHAT STAYED CONCEPTUALLY THE SAME
=========================================================

- Both use ExecutorService + Callable + Future for parallel data fetching.
- Both use the producer-consumer pattern (wait()/notifyAll()) for the
  reminder/notification pipeline.
- Both use a background Thread + sleep() + cooperative interrupt() for the
  guided breathing exercise.
- Both strictly follow the JavaFX thread-confinement rule: no background
  thread ever touches a UI control directly, always via Platform.runLater(...).
- Both deliberately keep an actual, visible, reproducible race-condition bug
  as a demo/diagnostic ONLY - neither version ships a real race condition in
  a live, user-facing feature. (v7 does this better - see Part 3, item 1 -
  but the design principle is the same in both.)
- Both name every background thread explicitly, rather than leaving threads
  with default names like "Thread-3".

CLOSING NOTE
=========================================================
v6 was built to satisfy a checklist: one tab per concept, one button per
demo. v7 solves the same checklist by building features that would exist in
a real health app anyway - and the concurrency is simply how those features
are implemented correctly. That's a meaningfully more advanced take on the
same assignment, and it directly answers the brief of making the
multithreading/concurrency work "real life applicable."
